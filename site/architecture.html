c python-cordis

Six modules. Three layers. One kernel.

内核只提供 6 个模块、3 个抽象层。具体的 agent 循环、LLM seam、会话日志、持久化、Web 传输 —— 都是上一层"应用层"的普通可替换插件,内核对它们一无所知。

The 6 modules

F1 — F6 · 六个核心模块

每个模块只做一件事,组合起来就是完整的插件化运行时。

#模块职责
F1core/hook.py · HookRegistrypluggy 之上的四种 hook 调用模式
F2core/context.py · Context反射式服务容器,scope chain,可逆效应
F3core/fiber.py · Fiber组件运行时实例,生命周期 + 反应式 reconcile
F4core/config.pyOmegaConf 加载/覆盖/插值,无代码执行
F5core/loader.py · Loader声明式组件加载,reconcile + hot_reload
F6core/hmr.py · Reloader事务化热重载,失败回滚
Layered architecture

三层:内核 ↔ 扩展插件 ↔ 应用

箭头方向是依赖关系:上层依赖下层,下层不知道上层的存在。绿色边框 = 内核模块;橙色 = 应用层插件。

Layer 3 · Application

你的业务 main.py

把若干 entry 列表丢给 Loader.reconcile,业务就跑起来了。换业务不需要改内核。

Layer 2 · Companion plugins

python-cordis-agent · LLM / web / persistence · …

应用层的"现成插件集":agent 循环、LLM seam、会话日志、持久化后端、Web 传输,均为可替换插件。

Layer 1 · Kernel

python-cordis · HookRegistry / Context / Fiber / Loader / HMR

6 个模块,约 1500 行 Python。零业务预设,只提供"让插件可组合"的最低限度机制。

# 一次最简单的"启动应用"
ctx     = Context()
hooks   = HookRegistry()
loader  = Loader(ctx, hooks)

entries = [
    {"module": "myapp.printer",  "config": {"prefix": ">"}},
    {"module": "myapp.logger",  "config": {"sink": "stdout"}},
]

loader.reconcile(entries)            # 增量 reconcile
loader.hot_reload("myapp.printer")  # 改文件 → 自动重载,失败回滚
Plugin discovery

插件入口点约定

python-cordis 自己不声明任何入口点插件;应用通过标准 python_cordis.plugins group 注册自己的插件。

# your-plugin/pyproject.toml
[project.entry-points.python_cordis.plugins]
my_plugin = "my_pkg.plugins:MyPlugin"
# your app
hooks = HookRegistry()
hooks.load_entry_points()             # 自动发现所有注册的插件
